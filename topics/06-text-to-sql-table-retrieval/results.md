# Results

Generated by `python -m tablefind.report` from the run files in `runs/`. Smoke runs (`--limit`) and runs stopped by the budget are left out.

**All found** = every table the question needs is in the 7 handed over. **Recall** = share of needed tables found. **Top-20 ceiling** = all needed tables were in the 20 the LLM was shown. **Made up** = answers naming a table it wasn't shown. **Filled from search** = when the LLM named fewer than 7 usable tables, the rest came from the search order: average tables filled per answer (share of answers with any fill). **$ / question** = repeat 1 only (later repeats hit the provider's prompt cache), without the one-time embedding of the 971 tables. **s / question** = wall time with parallel workers; **LLM s** = the re-ranker call alone. **Levels 4c, 4 and 5j hand over 10 tables, not 7**: level 3's picks plus 3 more, from the search order (4c, the control) or joined to the picks by a foreign key (4); 5j is level 5's picks plus 3 joined tables. They reuse level 3's or level 5's answers, so they cost nothing extra.

## Against the article

**Article says:** table recall goes up when an LLM re-ranks the search results, and again with descriptions (LinkedIn's Figure 6, no numbers given).

**We got (held-out, all found):** embedding search 22% → LLM re-rank 45% → + descriptions 55%. With 3 more tables (10 in all): from search 58%, joined by foreign key 75%. Pinterest-style summaries: 61%, plus 3 joined tables: 78%.
